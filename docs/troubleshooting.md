# 트러블슈팅 기록 — 문제, 원인, 해결

VisuPick 개발 중에 실제로 겪은 문제와 해결 과정을 모은 문서다. 각 모듈 문서(`bin_picking.md`, `kuka_communication.md` 등)는 "지금 코드가 어떻게 동작하는가"를 설명한다. 이 문서는 **"왜 지금 코드가 이렇게 생겼는가"**, 즉 그 모양이 되기까지 어떤 사고를 겪었는지를 기록한다.

이 문서를 쓰는 목적은 세 가지다.

1. **같은 증상을 다시 만났을 때** 원인 후보와 확인 방법을 바로 찾는다.
2. **코드를 고치기 전에** "이 줄이 왜 있는지"를 안다. 예를 들어 `WAIT SEC 0` 한 줄을 지우면 부품이 공중에서 떨어진다.
3. **경험을 설명할 때** 증상 → 가설 → 검증 → 해결 순서로 정리된 사례를 쓴다(면접 활용은 [§7](#7-면접에서-이야기할-때)).

각 사례는 같은 틀로 쓴다.

> **증상**(무엇이 보였나) → **원인**(진짜 이유) → **어떻게 찾았나**(진단 과정) → **해결** → **검증** → **교훈**

날짜는 커밋/작업 기록 기준이다. 자세한 수치와 경위는 괄호 안 커밋 해시로 `git show <해시>` 하면 볼 수 있다.

## 용어 몇 가지

- **KRL**: KUKA 로봇 컨트롤러에서 도는 프로그래밍 언어. 이 프로젝트는 [krl/ext_move.src](../krl/ext_move.src) 가 Python 이 넣어 준 모션 큐를 실행한다.
- **C3Bridge**: 로봇 컨트롤러의 변수를 TCP(포트 7000)로 읽고 쓰게 해 주는 서버 프로그램. Python 은 이걸 통해서만 로봇과 말한다([kuka_communication.md](kuka_communication.md)).
- **PTP / LIN**: 로봇 이동 방식. PTP 는 관절을 각자 움직여 빠르게 가는 방식(경로는 곡선), LIN 은 공구 끝을 직선으로 움직이는 방식.
- **OOM (Out Of Memory)**: 메모리를 더 할당할 수 없어서 생기는 오류. 여기서는 GPU 메모리.
- **마스크**: 이미지에서 "이 픽셀이 그 물체다"를 참/거짓으로 표시한 2D 배열. SAM3 가 만들어 준다.
- **OBB (Oriented Bounding Box)**: 물체에 맞춰 회전한 사각형.
- **회귀 테스트**: 고친 버그가 다시 생기지 않는지 확인하려고 그 버그 조건을 그대로 재현해 두는 테스트.

## 1. 하드웨어 · 네트워크 · 운영 환경

### 1.1 Percipio 카메라가 ping 은 되는데 검색이 안 된다

*2026-07-01 · 커밋 510155f 참고*

- **증상**: Percipio FM815 3D 카메라(네트워크로 연결하는 GigE 카메라)에 `ping` 은 응답하는데, SDK 의 `DiscoverCameras()` 는 0대를 반환했다. "Ubuntu 에서는 연결이 안 된다"는 상태로 SDK 문제부터 의심했다.
- **원인**: Ubuntu 방화벽 **ufw** 의 기본 정책이 "들어오는 연결 거부"다. GigE Vision 카메라 검색은 PC 가 **UDP 브로드캐스트**(포트 3956)를 보내고 카메라가 UDP 로 답하는 방식인데, 그 **응답이 방화벽에서 버려졌다**. `ping` 은 ICMP 라는 별개 프로토콜이라 방화벽에 안 걸려서, "네트워크는 정상"이라는 착시가 생겼다.
- **어떻게 찾았나**: "ping 은 되는데 검색은 안 된다" → 물리 연결·IP 는 정상 → 차이는 프로토콜(ICMP vs UDP) → 들어오는 UDP 를 막는 것이 무엇인지 확인 → `ufw status`.
- **해결**: 카메라 IP 만 허용하는 규칙 추가 (코드 변경 없음).
  ```bash
  sudo ufw allow from 192.168.0.74 comment 'Percipio GigE camera'
  ```
- **함께 나온 문제**: 같은 카메라가 정상 항목 + `InvalidNetCam` 항목으로 **두 번 검색**되는 경우가 있었다. 순서에 기대지 않고 유효한 항목만 고르도록 했다 — [percipio_camera.py:103](../percipio_camera.py#L103) `_select_valid_camera`. `libusb-1.0.so` 를 못 찾는 오류는 `libusb-1.0-0-dev` 설치로 해결했다(런타임 패키지는 `.so.0` 만 주고 버전 없는 링크는 dev 패키지에 있다).
- **교훈**: "ping 이 되면 네트워크는 정상"이 아니다. **어떤 프로토콜·포트로 통신하는지**까지 봐야 한다.

### 1.2 RealSense 가 USB 포트를 옮겨 다녀야 인식된다

*2026-07-02*

- **증상**: Intel RealSense D415 를 여러 USB 포트에 꽂아 봐야 겨우 인식되고, 아예 안 잡히는 날도 있었다.
- **원인**: **길고 정품이 아닌 USB 케이블**. D415 는 USB3(SuperSpeed)가 필수인데, 신호 품질이 나쁜 케이블은 반복해서 꽂을수록 더 나빠진다.
- **어떻게 찾았나**: `dmesg`(커널 로그)를 확인했다. 처음에는 `new SuperSpeed ... idVendor=8086` 으로 정상 인식된 기록이 있었고, 이후 USB 연결 끊김과 `-110`(타임아웃) 오류가 반복되다가 끝내 인식 자체가 안 됐다. 전형적인 케이블/커넥터 불량 패턴이다. 또 이 PC 의 USB 포트 중 일부는 USB2 버스(480M)라서 그 포트에서는 원래 동작할 수 없다는 것도 확인했다(`lsusb -t`).
  - 참고: `UVC non compliance ... error -5` 는 RealSense 에서 흔히 나오는 **무해한 메시지**다. 진짜 신호는 연결 끊김과 `-110`.
- **해결**: 짧은 인증 USB3 케이블로 먼저 확인하고, 거리가 필요하면 **액티브(리피터) USB3 케이블**이나 광 연장기를 쓴다. 수동형 긴 USB3 케이블은 동작하지 않는다. 소프트웨어 쪽에서는 연결 재시도(최대 3회)와 프레임 대기 타임아웃(5초)을 넣어 무한 대기를 막았다(커밋 7cffde5).
- **교훈**: 간헐적 장애는 소프트웨어보다 **물리 계층(케이블·전원)** 을 먼저 의심한다. 커널 로그에 답이 있다.

### 1.3 로봇과 통신이 안 된다 — 랜선 꽂은 포트가 틀렸다

*2026-07-03*

- **증상**: 로봇 IP(192.168.20.77)·포트(7000)가 맞는데 C3Bridge 연결이 실패했다.
- **원인**: KUKA KRC5 컨트롤러에는 이더넷 포트가 여러 개(XF1~XF8) 있고 **용도가 모두 다르다**. 외부 통신용 네트워크(KLI)는 **XF5/XF6** 이다. XF1 은 서비스용, **XF8 은 EtherCAT(모터 드라이브 버스)이라 PC 를 절대 꽂으면 안 된다.** 랜선이 엉뚱한 포트에 꽂혀 있었다.
- **해결**: PC ↔ XF5 직결. PC 쪽 네트워크 카드에 로봇 서브넷 고정 IP(192.168.20.100/24)를 줘야 하는데, `ip addr add` 로 넣은 값은 NetworkManager 가 계속 되돌렸다. 그래서 `nmcli` 연결 프로필(`robot-direct`)로 영구 설정했다.
- **교훈**: 산업용 컨트롤러의 포트는 "아무 데나 꽂는 랜 포트"가 아니다. **매뉴얼에서 포트별 용도**를 먼저 확인한다. 리눅스에서 수동 IP 가 사라지면 NetworkManager 를 의심한다.

### 1.4 Percipio 캡처가 16초 걸리거나 멈춘다

*2026-07-01*

- **증상**: 제조사의 Windows 뷰어로 깊이 품질을 튜닝하고 돌아온 뒤, 캡처가 첫 장 16초, 이후 프레임 없음(타임아웃), 가끔 5초 제한에 딱 맞춰 성공하는 등 불안정해졌다. 정상이면 한 장에 0.2~1초다.
- **원인**: 뷰어가 카메라에 남긴 트리거/LED 설정 때문에 **카메라 내부 트리거·스트림 파이프라인이 꼬인 상태**. 소프트웨어 재연결로는 풀리지 않았다.
- **해결**: **카메라 전원을 물리적으로 껐다 켜기**(PoE 포트를 끄고 15초 뒤 켜고, 초기화 40초 대기). 이후 뷰어를 다시 열기 *전에* 앱에서 캡처를 먼저 확인한다. 뷰어에서는 깊이 관련 값(IR 노출·게인, SGBM 필터)만 조정하고 **트리거 모드와 LED 설정은 건드리지 않는다.**
- **덤 — 점군 밀도는 해상도로 안 오른다**: 유효 깊이 비율이 24~28% 로 낮아 해상도를 1280×960 으로 올려 봤지만 그대로였다(되돌림). 이 카메라는 스테레오 정합(SGBM)으로 깊이를 계산하므로, 실제로 효과가 있는 것은 **SGBM 필터 파라미터와 IR 신호 세기**다. 필터를 완화하면 24% → 32% 로 늘지만 노이즈도 는다.
- **교훈**: 장비 상태가 이상해지면 "마지막으로 무엇을 바꿨나"를 먼저 따진다. 그리고 소프트웨어로 안 풀리는 상태가 있다는 걸 인정하고 전원 재투입을 절차로 만든다.

### 1.5 SAM3 모델 로드가 CUDA out of memory 로 실패

*2026-11-25 · 커밋 800d51c*

- **증상**: 예전에 잘 되던 "SAM3 검출" 버튼이 `torch.OutOfMemoryError: CUDA out of memory` traceback 을 내며 실패했다. 코드는 바뀐 게 없었다.
- **원인**: 같은 PC 의 **다른 사용자 계정이 vLLM(LLM 서버)을 띄워 GPU 메모리 48 GiB 중 약 44.9 GiB 를 선점**하고 있었다. vLLM 은 기본 설정에서 GPU 메모리의 약 90% 를 시작할 때 미리 잡아 둔다. SAM3 에게 남은 공간은 33 MiB 였다.
- **어떻게 찾았나**: 오류 메시지에 이미 단서가 있었다 — `Process 1860843 has 43.86 GiB memory in use`. `nvidia-smi` 로 그 PID 가 `VLLM::EngineCore` 임을 확인하고, `ps` 로 부모 프로세스와 소유 계정을 확인했다.
- **해결**:
  - 당장은 그 작업이 끝나기를 기다리거나, 소유자에게 `--gpu-memory-utilization` 을 낮춰 달라고 요청한다. 다른 사용자의 프로세스를 함부로 죽이지 않는다.
  - 재발 대비로 **앱이 원인을 직접 알려주게** 했다. 검출기의 모델 로드·추론 실패가 OOM 이면 `nvidia-smi` 로 GPU 를 쓰는 프로세스(PID·계정·사용량)를 조회해 "GPU 메모리 부족" 알림창으로 보여준다 — [object_detector.py:143](../object_detector.py#L143) `raise_if_gpu_oom`. 상세는 [bin_picking.md](bin_picking.md) "GPU 메모리 부족 알림".
- **교훈**: "어제는 됐는데 오늘은 안 된다"면 코드보다 **환경(공유 자원)** 을 먼저 본다. 그리고 사용자가 원시 traceback 대신 **원인과 할 일**을 보게 만드는 것도 해결의 일부다.

## 2. 로봇 통신 · 모션 · 안전

### 2.1 이동 중에 진공이 꺼져 부품을 떨어뜨린다

*2026-07-09 · 커밋 6a1cdf5*

- **증상**: 픽 사이클에서 부품을 집어 놓기 위치로 옮기는 **도중에** 진공이 꺼져 부품이 떨어졌다. Python 은 "이동 완료"를 확인한 다음에 진공을 끄도록 짜여 있었다.
- **원인**: KRL 의 **선행 실행(advance run)**. `$ADVANCE = 3` 이면 인터프리터는 로봇의 실제 움직임보다 **최대 3개 모션 앞서** 코드를 읽어 실행한다(경로를 부드럽게 이어 붙이려고). 그래서 "이 슬롯 완료"(`robo_motion_type[slot] = 0`)를 표시하는 줄이 **로봇이 아직 이동 중일 때** 실행됐다. Python 은 그 표시를 믿고 진공을 껐다.
- **해결**: 완료 표시 직전에 `WAIT SEC 0` 을 넣었다 — [krl/ext_move.src:123](../krl/ext_move.src#L123). 0초 대기지만 선행 실행을 멈추는 지점이 되어, 그 아래 줄은 **로봇이 실제로 도착한 뒤에** 실행된다. 이제 `0` 은 "명령 보냄"이 아니라 "물리적으로 도착함"을 뜻한다.
  - Python 쪽 사이클 실행기도 "진공·블로우·대기는 **앞선 모든 모션이 물리적으로 끝난 뒤에만**" 실행하는 규칙(그리퍼 배리어)으로 짰다.
- **검증**: 실제 로봇에서 픽 사이클 반복, 이동 중 낙하 없음.
- **교훈**: 다른 시스템이 주는 "완료" 신호가 **정확히 무엇의 완료인지** 확인해야 한다. 이 줄은 지우면 안 된다 — `ext_move.src` 를 고칠 때 반드시 유지한다. 상세는 [kuka_communication.md](kuka_communication.md) "`WAIT SEC 0` 가 왜 필요한가".

### 2.2 속도 30% 로 했는데 PTP 만 9% 처럼 느리다

*2026-07-09 · 커밋 6a1cdf5*

- **증상**: 속도 스핀을 30% 로 두면 LIN 은 그럭저럭인데 PTP 만 유난히 느렸다.
- **원인**: 사용자 % 를 **전체 속도 배율(`$OV_PRO`)과 관절 속도(`$VEL_AXIS`) 양쪽에 곱했다.** PTP 는 두 값을 모두 받으므로 실효 속도가 30% × 30% = **9%**(제곱 감속). LIN 은 관절 속도를 쓰지 않아 30% 그대로였다.
- **해결**: 사용자 % 는 `$OV_PRO` 에만 적용하고 관절 속도·가속은 고정 기준값(100% / 50%)으로 둔다 — [kuka_robot.py:674](../kuka_robot.py#L674) `set_speed`, 기준값 [kuka_robot.py:671](../kuka_robot.py#L671).
- **헷갈렸던 점**: T1(수동 저속) 모드에서는 수정 후에도 PTP 가 느렸다. 이건 **KUKA 안전 설계상 정상**이다(T1 은 공구 속도를 250 mm/s 로 제한하고 PTP 관절 속도를 보수적으로 낮춤). AUT(자동) 모드에서는 PTP 가 LIN 보다 빠른 것을 실기로 확인했다. **사이클 논리는 T1 에서, 속도는 AUT 에서 판단**한다.
- **교훈**: 하나의 사용자 손잡이는 **한 곳에만** 연결한다. 그리고 버그와 "원래 그런 동작"을 구별하려면 장비의 운전 모드 규칙을 알아야 한다.

### 2.3 출력 `$OUT` 에 직접 쓰면 거부된다

*2026-07-07 · 커밋 776aa95*

- **증상**: 진공 그리퍼 밸브는 로봇 디지털 출력 `$OUT[7]`(VAC_ON), `$OUT[8]`(VAC_Blow)에 연결돼 있다. 그런데 C3Bridge 로 `$OUT[7]` 에 쓰면 거부됐다. 사용자 변수나 `$OV_PRO` 는 잘 써졌다.
- **원인**: C3Bridge 변수 인터페이스가 **출력 직접 쓰기를 막는다**(읽기는 허용).
- **해결**: 비상정지(`robo_scram`)와 같은 **플래그 패턴**을 썼다. Python 은 사용자 변수 `robo_vac_on` / `robo_vac_blow` 에 목표값을 쓰고 `robo_vac_change = TRUE` 로 트리거를 세운다. KRL 의 인터럽트 83 이 이를 받아 `$OUT` 에 대신 적용하고 플래그를 내린다 — [krl/ext_move.src:28](../krl/ext_move.src#L28), [kuka_robot.py:640](../kuka_robot.py#L640) `set_vacuum`. Python 은 `$OUT` 을 다시 읽어 실제로 바뀌었는지 확인하고 실패하면 1회 재시도한다.
- **삽질 기록**:
  - 인터럽트 조건을 `WHEN (var <> $OUT[7])` 처럼 쓰면 **컴파일이 안 됐다**. 단순한 전역 BOOL 플래그만 안정적으로 동작했다.
  - 처음에는 출력 매핑 자체가 없어 보였다(I/O 단자에 배선이 없음). 예전 WorkVisual 프로젝트를 찾아보니 VAC_ON/VAC_Blow 매핑이 있었고, 이를 현재 프로젝트로 옮겨 배포했다.
  - 인터럽트는 `ext_move` 가 **실행 중일 때만** 동작한다. T1 에서는 Start 버튼을 떼면 프로그램이 멈춰 진공 명령도 멈춘다.
- **검증**: 실기에서 ON/OFF/블로우 원격 적용 약 0.3초.
- **교훈**: 통로가 막혀 있으면 **허용된 통로(사용자 변수) + 상대편 코드(KRL)** 로 우회한다. 이 변수와 인터럽트 번호는 Python 과 KRL 사이의 **계약**이라 반드시 양쪽을 함께 고친다.

### 2.4 Space 비상정지가 "로봇 연결" 버튼을 눌러버린다

*2026-08-26 · 커밋 e11f26e*

- **증상**: 연속 픽 도중 Space(비상정지 단축키)를 눌렀더니 **로봇 연결이 끊겼다.** 더 위험한 것은, 특정 상황에서는 **비상정지가 아예 걸리지 않았다**는 점이다.
- **원인**: Qt 에서 Space 는 **"지금 포커스를 가진 버튼을 누르는 키"** 다. 비상정지 단축키가 탭 안에만 등록돼 있었기 때문에, 탭 바깥의 "로봇 연결" 버튼에 포커스가 있으면 Space 가 단축키 대신 그 버튼을 눌렀다(→ 연결 해제). 버튼에 포커스가 있으면 비상정지 단축키 자체가 동작하지 않았다.
- **해결**:
  - 단축키를 **메인 윈도우에 하나만** 등록하고(`Qt.WindowShortcut`) 현재 탭으로 전달한다 — [main.py:1131](../main.py#L1131). 탭별로 중복 등록돼 있던 3개는 제거했다(같은 키가 여러 곳에 있으면 Qt 가 "모호함"으로 무시할 수 있다).
  - 모든 버튼을 `NoFocus` 로 만들어 Space 를 가로채지 못하게 했다 — [main.py:1140](../main.py#L1140). 버튼은 마우스로만 쓰므로 문제없다.
- **검증**: 로봇 연결 버튼, 연속 픽 시작 버튼, 캡처 버튼, 2D 뷰, 탭 밖 콤보 등 **어디에 포커스가 있든** 비상정지가 동작하고, 텍스트 입력칸에서는 공백이 정상 입력되는 것을 확인했다.
- **교훈**: 안전 기능은 "보통은 된다"가 아니라 **어떤 상태에서도 된다**를 검증해야 한다. GUI 프레임워크의 기본 키 동작을 모르면 안전 기능이 엉뚱한 동작으로 바뀐다.

### 2.5 비상정지 해제하면 작업이 반쯤만 이어진다

*2026-08-28 · 커밋 644ecdf*

- **증상**: 연속 픽 도중 비상정지 → 해제하면, 정지 직전 작업 몇 개만 실행되고 그다음은 사라졌다.
- **원인**: 비상정지가 Python 쪽 사이클 상태 기계를 **완전히 폐기**했다. 그런데 KRL 큐에는 **이미 보낸 모션이 남아 있어서**, 해제 순간 그것만 실행되고 끝났다. 두 시스템의 상태가 어긋난 것이다.
- **해결**: 비상정지를 "폐기"가 아니라 **"일시정지"** 로 바꿨다 — [robot_control_mixin.py:721](../robot_control_mixin.py#L721) `_cycle_pause`, [robot_control_mixin.py:766](../robot_control_mixin.py#L766) `_cycle_resume`.
  - 정지 시: 보낸 슬롯마다 실제 완료 여부를 읽어 **첫 미완료 단계로 되감고**, KRL 큐는 즉시 비운다(해제 순간 남은 모션이 멋대로 실행되지 않게).
  - 해제 시: "이어서 진행할까요?"를 묻고, 예를 누르면 미완료 단계부터 다시 보낸다.
  - 다시 보내도 안전한 이유: 목표가 **절대 좌표**라 멈춘 지점에서 같은 목표로 다시 갈 뿐이다. 진공·대기는 "모든 모션 완료 후" 규칙(2.1)상 되감기 구간에 끼지 않는다.
- **검증**: 스텁(가짜) 로봇으로 6가지 시나리오 확인 — 전송 중 정지, 재개 시 완료 단계 제외, 연속 픽 이어짐, 재개 거부, 대기 잔여 시간 보존, 비상정지 연타.
- **교훈**: 두 시스템(PC 와 로봇 컨트롤러)이 상태를 나눠 가지면, 중단·재개 시 **양쪽을 같이** 맞춰야 한다.

### 2.6 진공 호스가 점점 감긴다

*2026-08-28 · 커밋 0d130b4*

- **증상**: 픽을 반복할수록 그리퍼의 진공 호스가 한 방향으로 계속 감겼다.
- **원인**: 모든 이동을 **공구 좌표(Cartesian)** 로 보냈다. 같은 공구 자세를 만드는 관절 조합은 여러 개다(예: 손목 회전 A = −170° 와 +190° 는 같은 자세). 로봇은 그중 "현재 관절에서 가까운" 해를 스스로 고르는데, 손목 관절 A6 는 ±350° 까지 돌 수 있어서 이 선택이 반복되며 한쪽으로 누적됐다.
- **먼저 실패한 시도**: Cartesian A 각도로 경유점을 넣어 되돌리는 로직 → 효과가 없었다. Cartesian 목표로는 **어느 관절 해를 고를지 지정할 수 없기 때문**이다. 이 코드는 제거했다.
- **해결**: Home·놓기 위치를 티칭할 때 **관절 각도(`$AXIS_ACT`)도 함께 저장**하고, 두 위치로 갈 때는 **관절 좌표 PTP** 로 이동한다 — [kuka_robot.py:553](../kuka_robot.py#L553) `add_move_axis`. 관절 목표는 해가 하나뿐이라 결과가 결정적이다. 매 사이클 Home 복귀가 곧 A6 리셋이 되어 감김이 누적되지 않는다.
  - 관절값이 없는 예전 저장 파일은 Cartesian 으로 폴백하고 재티칭을 안내한다(로봇이 그 위치에 있다는 보장이 없으므로 현재 관절값을 자동으로 채우지 않는다).
- **검토한 대안**: A6 소프트 리밋 축소(전문가 권한 필요), 자세 + Status/Turn 지정(KRL 계약 변경 필요), 회전 피팅(하드웨어 작업). 소프트웨어만으로 되는 관절 티칭을 택했다.
- **검증**: 실기(KR C5)에서 호스가 꼬이지 않음을 확인. 상세는 [bin_picking.md](bin_picking.md) "관절 좌표 티칭 — 진공 호스 꼬임 방지".
- **교훈**: 로봇에서 "같은 자세"와 "같은 관절 상태"는 다르다. 케이블·호스가 달린 축은 **관절 공간**에서 제어해야 한다.

## 3. 비전 알고리즘

배경: 화장품 케이스(클램셸)를 진공으로 집으려면 **뚜껑이 열리는 방향**을 알아야 한다. 정사각형 케이스는 네 변 중 어디가 힌지(경첩)인지 골라야 해서, 이 판정 알고리즘에서 버그가 연달아 나왔다. 알고리즘 본문은 [bin_picking.md](bin_picking.md) §3.4.

### 3.1 여는 방향이 매번 바뀌는데 신뢰도는 0.96

*2026-09-18 · 커밋 b3ba6ae*

- **증상**: 가만히 있는 장면인데도 여는 방향이 매번 바뀌고 정반대로도 나왔다. 그런데 화면에 표시되는 신뢰도는 **0.96** 이었다.
- **원인**: 신뢰도를 `(1등 − 2등) / (1등 − 4등)` 으로 계산했다. 이건 **상대** 격차라 스케일이 사라진다. 네 변 점수가 0.115 / 0.092 / 0.092 / 0.091 로 사실상 동점이어도, 비율로는 크게 나온다.
- **어떻게 찾았나**: 합성 장면을 20회 반복 실험했다. SAM3 마스크가 투명한 힌지 부분을 덮지 못하면 네 변이 모두 케이스 본체가 되어 판별 근거가 없어진다. 정답률은 3/20 으로 네 방향에 고르게 흩어졌다.
- **해결**: 신뢰도를 **절대 격차** `clip(1등 − 2등, 0, 1)` 로 바꿨다. 근거가 있을 때 0.81~0.89, 없을 때 0.00~0.06 으로 확실히 갈린다. 저신뢰 경고 임계도 방식별로 나눴다.
- **교훈**: **틀린 답보다 나쁜 건 확신하는 틀린 답**이다. 지표는 "근거가 없음"을 드러낼 수 있어야 한다.

### 3.2 히스토그램 상관이 네 변을 동점으로 만든다

*2026-09-18 · 커밋 c3e0ab2, 0f7b493*

- **증상**: 실제 분홍 케이스 사진에서, 눈으로는 위쪽 은색 힌지가 뚜렷한데 알고리즘은 10회 중 5회 오답을 냈다. 띠 두께를 조금만 바꿔도 답이 튀었다.
- **원인**: 변마다 색 분포를 **히스토그램 피어슨 상관**으로 비교했다. 상관은 두 분포가 겹치지 않으면 "얼마나 먼지"와 상관없이 비슷한 값으로 **포화**된다. 실측에서 네 변 점수가 0.15~0.18 안에 몰렸다.
- **해결**: 각 변 띠의 색이 **케이스 본체 색에서 얼마나 벗어났는지**를 Lab 색 공간의 a\*b\* 평면 **거리**로 잰다. 같은 사진에서 점수가 [3.43, 0.89, 1.37, 1.91] 로 확실히 갈렸고, 띠 두께 10~30% 전 구간에서 정답이 나왔다. 띠 두께 기본값도 25% → 15% 로 줄였다(힌지 바는 케이스의 약 8% 라 25% 는 신호를 3배 희석).
- **후속 정리**: 히스토그램 기반 대안 두 개(배경 유사도·이질도)는 실측 8회 비교에서 실패가 잦아 **선택지에서 제거**했다. "그럴듯한데 틀리는" 옵션을 남겨 두지 않기 위해서다. 제거 이유와 수치는 [opening_analysis.py](../opening_analysis.py) 상단 주석에 남겼다.
- **교훈**: 유사도 지표를 고를 때 **"다르다"와 "얼마나 다르다"를 구분할 수 있는지** 확인한다. 합성 데이터에서 통한 방법도 **실물 사진을 테스트 fixture 로 고정**해 검증해야 한다.

### 3.3 마스크 침식이 전혀 동작하지 않았다

*2026-09-18 · 커밋 0f7b493*

- **증상**: 3.2 정리 작업 중, 근거가 없는 장면에서도 신뢰도가 0.45 까지 나오는 것을 발견했다.
- **원인**: 마스크 가장자리의 배경 픽셀을 깎아 내려고 `cv2.erode` 를 썼는데, **기본 경계값이 "최댓값"** 이라 이미지 가장자리는 깎이지 않는다. 그런데 회전 보정한(warp) 마스크는 이미지를 꽉 채우므로 **침식이 통째로 무효**였다(픽셀 수 25440 → 25440). 마스크가 2px 만 삐져나와도 그 변이 배경색을 머금었다.
- **해결**: `borderType=cv2.BORDER_CONSTANT, borderValue=0` 을 명시 — [opening_analysis.py:485](../opening_analysis.py#L485). 같은 장면의 신뢰도가 0.001~0.017 로 정상화됐다.
- **교훈**: 라이브러리 함수의 **기본값이 내 상황에서 무엇을 의미하는지** 확인한다. 처리 전후 픽셀 수처럼 **눈에 보이는 수치로 "정말 동작했는지"** 확인하는 습관이 이런 조용한 버그를 잡는다.

### 3.4 검은 케이스에서 여는 방향이 정반대

*2026-09-22 · 커밋 0ff392b*

- **증상**: 3.2 수정 후 분홍 케이스는 잘 되는데, 거의 검은색인 다른 제품에서는 방향이 정반대로 나왔다.
- **원인**:
  - 검은 본체는 무채색이라 **색으로는 신호가 없다**. 네 변의 색 편차가 1.53~2.27 로 모두 노이즈 수준이었다.
  - 그 노이즈 안에서 1등이 된 건 아래쪽에 인쇄된 **흰색 로고**였다. 그래서 아래 변이 힌지로 뽑혔다.
  - 진짜 힌지(위쪽 투명 띠)는 **밝기**로 뚜렷했다(위 25.7 vs 나머지 2.5~3.6).
  - 그런데 분홍 케이스를 밝기로 보면 요철 그늘에 속아 오답이 난다. **한 가지 단서로는 두 제품을 모두 풀 수 없다.**
- **해결**: 색(a\*b\*)과 밝기(L) 두 벌로 점수를 계산하고, **1·2등 격차가 큰 쪽을 자동 채택**한다 — [opening_analysis.py:468](../opening_analysis.py#L468). 각 점수는 본체 내부의 자연스러운 흔들림(MAD, 중앙값 절대 편차)으로 나눠 정규화해서, 원래 많이 흔들리는 채널(그늘이 많은 밝기 등)은 자동으로 깎인다. 어느 단서를 썼는지(`feature`)를 결과와 디버그 화면에 표시한다. 사용자가 조정할 값은 늘리지 않았다.
- **검증**: 실물 2종 × 띠 두께 6종 = 12가지 설정 **전부 정답**, 매번 기대한 단서를 선택(분홍 → 색, 검정 → 밝기). 검은 케이스 사진도 `tests/data/` 에 고정했다.
- **교훈**: 하나의 제품으로 튜닝한 규칙은 **다른 제품에서 정반대로** 틀릴 수 있다. 해결책은 제품별 스위치가 아니라 **데이터가 스스로 더 믿을 만한 단서를 고르게** 하는 것이었다.

### 3.5 쉼표로 여러 객체를 적으면 아무것도 못 찾는다

*2026-09-14 · 커밋 68db0f0*

- **증상**: SAM3 텍스트에 `rectangle, circle` 을 넣으면 0개 검출. 입력칸 안내문 예시가 "(예: cosmetic case, transparent box)" 라 오히려 이렇게 쓰도록 유도하고 있었다.
- **원인**: SAM3 의 `set_text_prompt` 는 **한 번에 명사구 하나**만 받는다. 입력 전체가 "rectangle, circle" 이라는 낯선 명사구 하나로 전달됐다.
- **해결**: 쉼표로 나눠 개념마다 따로 호출한다 — [object_detector.py:283](../object_detector.py#L283) `split_prompts`. 무거운 이미지 임베딩은 1회만 계산해 재사용하므로 2종이어도 시간은 약 1.5배(130 → 385ms). 같은 물체가 두 개념에 모두 걸리면 겹침(IoU ≥ 0.85) 기준으로 점수 높은 쪽만 남긴다 — [object_detector.py:299](../object_detector.py#L299).
- **교훈**: 외부 모델 API 의 **입력 단위**를 확인한다. UI 예시 문구도 사용 방법을 만든다.

### 3.6 Bin Box 가 재시작하면 사라진다

*2026-09-18 · 커밋 4f2468a*

- **증상**: 작업 영역(Bin Box)을 설정해 두고 앱을 재시작하면 화면에 안 보였다. 저장·로드가 깨졌다고 의심했다.
- **어떻게 찾았나**: 직전 리팩터링을 의심해, 리팩터링 전후의 관련 함수 12개를 **AST(코드 구문 트리)로 비교**했다. 2개만 바뀌었고 나머지는 완전히 동일했다. 실제 저장 파일로 끝까지 실행해 보니 폴리곤이 정상 투영됐다. **저장·로드·표시 코드는 정상**이었다.
- **진짜 원인**: Bin Box 는 로봇 좌표계에 저장되므로 화면에 그리려면 **캘리브레이션과 캡처가 모두 필요**하다. 그게 없을 때 뜨는 "캘리브레이션 로드 필요" 경고가 **바로 뒤의 "캡처 완료" 메시지에 즉시 덮여** 사용자가 이유를 볼 수 없었다.
- **해결**: 표시 함수가 성공 여부를 반환하고, 캡처 완료 메시지에 "⚠ 저장된 Bin Box 를 표시하지 못함: 캘리브레이션을 로드하세요" 를 붙인다 — [bin_picking_tab.py:2262](../bin_picking_tab.py#L2262).
- **교훈**: "기능이 고장났다"는 신고가 실은 **"왜 안 되는지 알 수 없다"** 인 경우가 많다. 코드를 고치기 전에 정말 고장인지 증거로 확인하고, 사용자에게 보이는 메시지가 사라지지 않는지도 본다.

### 3.7 실시간 추적 중 43프레임에서 IndexError

*2026-09-22 · 커밋 3c1af36*

- **증상**: SAM3 실시간 검출 + 객체 추적 중 43번째 프레임 근처에서 `IndexError` 로 멈췄다.
- **원인**: 추적기의 `update()` 가 매칭 결과를 트랙 목록의 **인덱스(번호)** 로 들고 있었다. 그런데 오래된 트랙을 지워 목록을 다시 만든 **뒤에** 그 번호로 트랙을 찾았다. 앞쪽 트랙이 지워지면 뒤쪽 번호가 밀린다. 그래서 엉뚱한 트랙을 가리키거나(= ID 가 **조용히** 뒤바뀜), 맨 끝 번호였다면 IndexError 가 났다.
- **해결**: 매칭하는 **그 자리에서** (검출, 트랙 객체) 짝을 모은다 — [tracking.py:366](../tracking.py#L366). 객체 참조라 이후 목록이 바뀌어도 영향이 없다.
- **검증**: "앞 트랙이 만료되는 바로 그 프레임에 뒤 트랙이 매칭되는" 조건을 회귀 테스트로 만들고, **수정 전 코드에서 같은 줄의 IndexError 가 재현되는 것**을 먼저 확인한 뒤 고쳤다. 트래커 3종 모두에 적용.
- **교훈**: 목록을 수정하는 코드 앞뒤로 **인덱스를 보관하지 않는다**. 더 무서운 건 터지지 않는 쪽(ID 가 조용히 뒤바뀜)이다 — 크래시는 그나마 드러난 운 좋은 경우다.

## 4. 의존성 · 리팩터링 · 구조

### 4.1 라이브러리 하나 설치했더니 다른 기능이 조용히 죽었다

*2026-09-22 · 커밋 58ece5f*

- **증상**: 객체 추적에 `roboflow/trackers` 패키지를 써 보려고 설치했더니, 테스트는 모두 통과하는데 **CAD 매칭의 PPF 와 표면 추적의 선 검출이 동작하지 않았다.**
- **원인**:
  1. trackers 는 `numpy>=2.0.2` 를 요구하는데 SAM3 는 `numpy<2` 가 필요하다 → 정면 충돌.
  2. trackers 가 `opencv-python` 을 끌어와 기존 `opencv-contrib-python` 과 **섞였다.** 그러자 contrib 에만 있는 `cv2.ppf_match_3d`(PPF)와 `cv2.ximgproc.thinning`(선 검출)이 고장 났다.
  3. 이 고장은 `hasattr` 로 확인하면 True 라 **실제로 호출해야만** 드러난다. 그래서 pytest 도 통과했다.
- **해결**: 환경을 원복(numpy 1.26.4 / opencv-contrib 4.10.0.84)하고, 실제 호출로 PPF·thinning 이 되살아난 것을 확인했다. 추적기는 **새 의존성 없이** 직접 구현했다(scipy 헝가리안 할당만 사용) — [tracking.py](../tracking.py). [requirements.txt:46](../requirements.txt#L46) 에 설치 금지 경고와 이유를 남겼다.
- **교훈**: 의존성 하나는 **환경 전체**를 바꾼다. 특히 OpenCV 는 `opencv-python` 과 `opencv-contrib-python` 이 같이 깔리면 안 된다. "import 가 된다 = 동작한다"가 아니다.

### 4.2 모듈 분리 후 CAD 로드에서 NameError

*2026-08-28 · 커밋 602b1fc*

- **증상**: CAD 파일을 열면 `NameError: name 'Path' is not defined`.
- **원인**: 알고리즘을 탭 파일에서 [cad_registration.py](../cad_registration.py) 로 옮기면서 새 파일에 `from pathlib import Path` 를 빠뜨렸다. `Path` 를 쓰는 함수가 하나뿐이라 import 확인에서는 안 걸리고 **호출 시점에** 터졌다.
- **해결**: 한 군데만 고치지 않고, 분리한 세 모듈을 **AST 로 전수 검사**해 정의되지 않은 이름을 모두 찾았다. `line_tracking.py` 의 `Dict` 누락도 함께 나왔다(타입 주석에만 쓰여 아직 안 터졌던 잠복 버그). 그 경로의 회귀 테스트를 추가했다(커밋 319fe2b).
- **교훈**: 버그 하나를 고칠 때 **같은 종류의 버그를 전부** 찾는다. 코드를 옮기는 리팩터링은 "옮긴 코드가 실제로 실행되는" 테스트가 있어야 안전하다.

### 4.3 오류 처리 코드가 오히려 오류를 낸다

*2026-09-22 · 커밋 58ece5f*

- **증상**: (실제 사고 전에 발견) 검출기 예외가 나면 오류창 대신 `NameError` 가 날 상태였다.
- **원인**: `bin_picking_tab` 이 `DetectorUnavailable` / `DetectorError` 를 **한 함수 안에서만** import 했는데, 다른 함수의 `except (DetectorUnavailable, DetectorError)` 가 그 이름을 썼다. 예외가 실제로 나기 전까지는 `except` 줄이 평가되지 않아 드러나지 않는다.
- **해결**: 모듈 맨 위로 import 를 올렸다 — [bin_picking_tab.py:68](../bin_picking_tab.py#L68).
- **교훈**: 예외 처리 경로는 평소에 실행되지 않아 **가장 테스트가 덜 된 코드**다. 일부러 예외를 일으키는 테스트로 확인한다.

### 4.4 Percipio 설정 로드가 성공한 척했다

*2026-07-01~07 · 커밋 510155f*

- **증상**: 뷰어에서 만든 설정 파일(.fea)을 앱에서 불러와도 아무 변화가 없었는데, 앱은 "성공"이라고 했다. 왜곡 보정도 꺼진 채였다.
- **원인** (세 가지):
  1. `LoadFeaturesFromFile` 은 상태값이 아니라 **튜플 `(status, info)`** 를 반환한다. `if not status:` 로 판정하면 튜플은 항상 참이라 **항상 성공**으로 보였다 — [percipio_camera.py:278](../percipio_camera.py#L278).
  2. 이 함수는 **캡처 중에는 실패**한다. 캡처 정지 → 로드 → 캡처 재시작으로 감쌌다.
  3. `SetUndistortionEnabled(True)` 로 불렀는데 실제 시그니처는 `(sensor_id, enable)` 이었다. 예외가 조용히 삼켜져 왜곡 보정이 꺼져 있었다 — [percipio_camera.py:195](../percipio_camera.py#L195).
- **교훈**: SDK 반환값은 **문서(또는 `.pyi` 타입 파일)로 형태를 확인**한다. `except: pass` 처럼 예외를 삼키는 코드는 버그를 숨긴다.

### 4.5 무거운 계산 중에는 비상정지가 안 먹는다

*2026-08-28 · 커밋 a315ac9*

- **증상**: CAD 매칭(수 초~수십 초) 동안 UI 가 멈췄고, 코드 리뷰에서 **그 사이 비상정지가 동작하지 않는다**는 안전 문제가 지적됐다.
- **원인**: 계산이 UI 스레드에서 돌면서 `processEvents()` 를 곳곳에 넣어 화면을 억지로 갱신했다. 비상정지는 그 호출 사이에서만 반응했다.
- **해결**: 매칭을 별도 스레드 워커(`QThread`)로 옮겼다 — [cad_matching_tab.py:95](../cad_matching_tab.py#L95) `MatchWorker`. 위젯 값은 시작 전에 UI 스레드에서 모두 읽어 넘기고, 워커는 Qt 위젯을 건드리지 않으며, 결과는 시그널로 돌려받는다.
- **일부러 옮기지 않은 것**: SAM3 추론은 **CUDA 컨텍스트가 스레드에 묶여 있어** 실기 검증 없이 옮기기 위험하다. 대신 실시간 검출은 `QTimer` 로 한 틱에 한 프레임만 처리하고 이벤트 루프로 돌아가서, 프레임 사이에 비상정지가 반응한다([cad_matching.md](cad_matching.md) 9.5절).
- **교훈**: 로봇 앱에서 UI 응답성은 편의가 아니라 **안전 요구사항**이다. 동시에 "모든 걸 스레드로"가 정답은 아니다 — 옮길 수 없는 이유가 있으면 그 이유를 기록하고 다른 방법을 쓴다.

## 6. 새 문제를 기록하는 법

문제를 해결하면 **같은 작업 안에서** 이 문서에 사례를 추가한다.

1. 알맞은 장(1~4)에 `### 번호 제목` 을 추가한다. 제목은 **증상**으로 쓴다(나중에 증상으로 찾게 되므로).
2. 증상 → 원인 → 어떻게 찾았나 → 해결 → 검증 → 교훈 순서로 쓴다. 해결에는 `file:line` 링크를 건다.
3. 맨 위 "한눈에 보기" 표에 한 줄을 추가한다.
4. 커밋 메시지에도 원인과 검증을 남긴다. 이 문서의 많은 내용이 커밋 메시지에서 왔다.

## 7. 면접에서 이야기할 때

면접 질문 "어려웠던 문제와 해결 경험"에는 **STAR** 구조(상황 Situation → 과제 Task → 행동 Action → 결과 Result)로 답하는 것이 일반적이다. 이 문서의 사례 틀이 그대로 대응한다: 증상 = 상황/과제, 어떻게 찾았나 + 해결 = 행동, 검증 = 결과, 교훈 = 배운 점.

이야깃거리로 특히 좋은 사례:

| 사례 | 보여줄 수 있는 역량 |
|---|---|
| **2.1** 이동 중 진공 OFF | 로봇 컨트롤러 내부 동작(선행 실행) 이해, 시스템 간 "완료" 의미 맞추기, 실기 검증 |
| **2.4** Space 비상정지 | 안전 기능을 "모든 상태"에서 검증, GUI 프레임워크 이해 |
| **2.6** 호스 꼬임 | 실패한 시도와 그 이유, 대안 비교 후 선택(관절 공간 vs Cartesian) |
| **3.1 → 3.4** 여는 방향 판정 | 가설 → 측정 → 실패 → 개선의 반복, 지표 설계, 실데이터 회귀 테스트 |
| **4.1** 의존성 충돌 | 라이브러리 도입 판단, "테스트 통과 ≠ 동작" 인식, 직접 구현 결정 |
| **1.5** GPU OOM | 공유 환경 진단, 사용자 경험까지 해결(원인 안내) |

말할 때 팁:

- **숫자**를 넣는다. "정답률 3/20 → 근거 없을 때 신뢰도 0.06 이하", "PTP 실효 9% → 30%", "12가지 설정 전부 정답".
- **실패한 시도**도 말한다(2.6 의 경유점 로직, 3.2 의 히스토그램 지표). 왜 안 됐는지 설명할 수 있으면 이해의 깊이가 드러난다.
- **재발 방지**로 마무리한다. 회귀 테스트, 문서, 사용자 안내 등 "다시는 같은 문제로 시간을 쓰지 않게 무엇을 남겼나".
